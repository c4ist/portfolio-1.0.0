The review queue in [Ledgerline](/work/ledgerline) is the fastest interface I have built, and the reason is not rendering performance. It is that a trained user never has to move their hand to the mouse.

## Design for the second hour, not the first minute

A tool used once a month should be discoverable. A tool used all day should be fast. These pull in different directions, and most internal software optimises for the demo rather than the job.

For a queue, the job is: look, decide, move on. That loop should cost one keystroke. Everything else — filters, bulk actions, the audit trail — can live behind a pointer.

## What it actually takes

Native elements first. A `<button>` is already focusable, already announces its role, and already responds to Enter and Space. Every `<div onClick>` is a keyboard bug you have not found yet.

Roving tabindex inside the list. Tab moves between the queue and the surrounding chrome; arrow keys move within it. The active row is `tabindex="0"` and every other row is `-1`, so Tab never walks two thousand items.

A visible focus indicator you did not weaken. `:focus-visible` gives keyboard users a ring without showing it to people clicking around, and it costs one rule. If you replace the browser default, check the replacement against every colour it crosses, including the selected row.

Focus that returns. Opening a detail panel moves focus in and marks the background `inert`; closing it puts focus back on the row you came from. Without the second half, dismissing a panel drops the user at the top of the document.

## The part nobody demos

Escape closes things. Enter confirms. Nothing traps focus in a widget with no way out. These are not accessibility extras bolted on at the end — they are the same work that makes the tool fast for the person who uses it eight hours a day.

Accessibility and speed are the same feature wearing different clothes.
